# Caching GPU lookups without losing device switching

## Overview

I worked on [ROCm/iris issue #590](https://github.com/ROCm/iris/issues/590), which asked to avoid repeating the GPU runtime lookup in `get_num_xcc()`. I added a cache keyed by the resolved device ID, plus tests for device switching. The change was merged as [PR #638](https://github.com/ROCm/iris/pull/638). I also built and revised issue-scout, a tool for checking whether an issue is a good contribution target; it helped me evaluate the issue and ultimately found one that matched with my needs.

## What happened

I started with issue-scout, for which I wrote the search strategy and the issue-fit rubric. My first scan rejected all five candidates because of a ranking rule I initially overlooked in the skill development - I sorted by “most recently updated,” which promoted brand-new repositories that could not pass the maturity checks. So I changed the strategy to exclude issues created in the previous 48 hours, and to break ties by oldest `createdAt`. I also added a required release-recency check, with “unclear” for repositories that had never published a release.
The first five candidates were all from repositories created within hours of the scan; after the strategy change, the next scan returned two candidates from `tjcsl/ion`, a promising repository, though the latest release was dated 2016-08-24. I changed the rubric after seeing that gap rather than treating recent commits as enough evidence of project health. With my modified rubric, I found issue #590. While the tool still rejected it because the repository had no GitHub Release, upon manual re-reading, I realized that a continuously-shipped repo that just doesn’t use GitHub Releases is not a genuine sign of staleness. So, I kept that result visible and made the decision myself after reading the issue and the already-merged PR #595, which had cached the sibling function but left `get_num_xcc()` uncached.
Before changing code, I wrote an isolated reproduction. It mocked the GPU runtime and called `get_num_xcc(device_id=0)` five times. The recorded result was: “`hipDeviceGetAttribute` call_count over 5 calls = 5.” This showed repeated calls, not a measured wall-clock performance cost. My first reproduction write-up did not meet my own repro-check standard. It made an overbroad claim, contradicted itself about the already-fixed `get_rocm_version()`, and pointed to a script that readers could not access. After two rejected rounds, I made the setup commands self-contained, narrowed the claim to the mocked call count, and pasted the script into the report. The next check accepted it.
The implementation resolves `device_id=None` to the current device before entering a private `lru_cache` helper. This matters because caching the public function directly could cache the literal `None` and return the first device’s result after the active device changed. My before/after reproduction showed the attribute lookup count dropping from five to one for five calls on the same device. I initially tested repeated calls, explicit device IDs, and the default path with a fixed device. A reviewer pointed out that all three tests could still pass if the public function cached `None` incorrectly. The review said: “None of the three tests checks that … the current device [changes].” I added `test_get_num_xcc_default_follows_current_device`, which switches devices 0 → 1 → 0 and expects XCC counts `[8, 4, 8]` with two attribute lookups. I also shortened the code comment the reviewer flagged.
I could not run the committed pytest file locally because my environment could not load PyTorch (`libtorch_cpu.dylib` was missing). Instead, I verified the assertions against the real `hip.py` through an isolated-import harness, and I reported the limitation rather than claiming pytest passed. The ROCm reviewer separately reported that the tests passed on MI355X with ROCm 7.2.1, and measured `get_num_xcc(0)` changing from 547 ns to 37 ns. Those hardware results are the reviewer’s, not mine.
My ship-gate recorded clean Ruff lint and format checks and a passing PR-precheck after I corrected a GitHub CLI path problem. I kept the change to `hip.py` and the new test file, and the PR was merged on November 13, 2026.

## Limitations and what's next

I did not have AMD hardware, so I could not produce local hardware timings or run the committed test through the full package import path. The reviewer’s hardware validation filled part of that gap, but I would set up a reliable ROCm test environment or CI run with that resource, if possible. 
- I would also include a current-device-switching test in the first version of a cache change. The review caught a test gap before merge, and that is the test I want to make routine for future caches whose default depends on changing runtime state.
